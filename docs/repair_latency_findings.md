# NLRC 修复耗时波动排查

排查时间：2026-11-18，Asia/Shanghai。采用代码检查和服务器只读诊断，未修改部署程序、限速规则或存储块。

## 结论与证据边界

当前运行环境的 IFB 入站限速队列确实在源块汇聚读取期间丢包；同一条带、同一执行节点、同一源块集合的只读检查也出现明显耗时波动，并观察到约 1 秒的 TCP 建连等待。这是已发现、应优先处理的网络问题。修复路径逐块新建连接并等待全部源块，将慢连接或重传的等待传递给总修复时间。

未复现截图中的 9.55789 秒完整修复，未采集该次运行的抓包或分阶段计时，因此不能声称已证明那一轮所有额外时间都来自 IFB 丢包，也不能仅凭一次约 1 秒的建连时间断言其具体重传次数。

## 当前服务器配置

- 编码：NLRC，k=96，r=3，z=7，NodeNum=106。
- BlockSize=4194304，即 4 MiB；L0 源块为 D0–D23，共 96 MiB。
- 相关存储节点的 eth0 和 ifb0 配置了 HTB，受限类显示 rate/ceil 约 2097 Mbit/s。
- IFB 的 HTB 根队列显示 direct_qlen=32，并已有累计 drops。direct_qlen 不是整个 HTB 类树的队列容量，不能据此把所有受限流量的队列长度断言为 32。
- 排查快照中相关节点空闲、可用内存约 21 GiB，未启用 swap；这不代表已排除截图发生时的临时资源竞争。
- 服务器 /root/HLRC 中 proxy.cpp、coordinator.cpp 的 SHA-256 与本地文件相同；此检查本身不证明运行二进制与源码完全一致。

## 只读复查

使用已有条带的 D0–D23，事先确认所有源文件大小正确。检查程序在对应的 L0 proxy 所在主机运行，通过生产 peer gateway 的 Get 协议读取完整源块；不计算修复结果、不写回、不创建新条带。每块新建 TCP 连接，使用有界并发。检查未做全程负载隔离。

这些是读取阶段的诊断数据，不应直接当作完整修复耗时或正式性能基准。Python 实现、缓存状态、运行顺序和样本量都限制了并发度比较的结论。

stripe 34 的 1.070190 秒一轮中：

- D21（172.16.2.155）：TCP 建连 1.027188 秒，等待就绪 0.003408 秒，接收数据 0.033415 秒。
- D23（172.16.2.158）：TCP 建连 1.019911 秒，等待就绪 0.003351 秒，接收数据 0.032773 秒。

8 路并发的 1.353007 秒一轮中，D23 建连仍耗时 1.018276 秒。因此当前证据不支持“只要减少为 8 路并发就能消除异常”。

最后两轮额外采样的接收端 TCPSynRetrans、TCPTimeouts、ListenDrops 等计数增量均为 0；这两轮没有约 1 秒的建连异常。此前出现异常建连的一轮未记录这些 TCP 计数增量。大块数据的 TCP 重传主要应在源发送节点核查，不能拿接收端 RetransSegs=0 来排除它。

## 代码中放大等待的路径

- project/src/proxy.cpp：GetFromOwnerProxy 每个源块重新 connect，同步等待状态与全部数据；没有应用层传输 deadline。
- project/src/proxy.cpp：custom recovery 为每个源块启动一个读取线程，join 所有线程后才解码；任意一个源块延迟都会推迟修复完成。
- project/src/coordinator.cpp：customRecovery 使用 steady_clock 计时，覆盖计划、proxy RPC、读取、计算及写回等待。
- limit_common.sh：setup_htb 创建受限/非受限类，没有显式配置这些类的叶子队列策略或容量；实际应结合 tc 的类、队列、过滤器和 IFB 参数一起检查。
- 正常 set 路径会等待各 AppendToDatanode 的 RPC 完成，datanode 的 handleAppend 也会 join 写入线程；未发现正常返回 set 成功却完全不等待块写入的代码证据。flush/close 不等同于 fsync。

## 建议的处理顺序

1. 保留实验设定的带宽，先明确配置 IFB/HTB 受限类的叶子队列策略与容量，检查多流汇聚时的丢包和公平性。
2. 在实际 custom recovery 路径添加阶段日志：协调器准备/调用耗时、每源块建连/状态等待/接收时间、系数求解、解码、每输出块写回、总耗时。关联 stripe、目标节点、块号和源 IP。
3. 以固定条带/固定节点重复采样，记录每轮接收端 drops 与发送端 TCP 重传/超时增量；再比较限速队列调整前后的中位数、p95、最大值。
4. 将读取并发度做成可配置参数，比较 8/16/24；随后考虑连接复用。单独降低并发数尚未在本次检查中解决丢包问题。
5. 为网络等待加入明确超时与失败报告。超时能限制挂起时间，但不能被当成修复成功或降低修复时间的算法优化。
